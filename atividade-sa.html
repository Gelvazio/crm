Contextualização

Uma equipe comercial controla clientes, produtos e vendas em planilhas e perde pedidos por erros simples. Um deles é a condição de pagamento: alguém cadastra uma condição sem nome ou com zero parcelas, e o pedido sai com a forma de pagar errada. Antes de trocar a planilha por um CRM, o gestor exige que cada parte do sistema nasça com testes automatizados, para que uma alteração futura não quebre o que já funciona (teste de regressão).

O CRM é um projeto Vite com um arquivo JavaScript por assunto. O docente já implementou o cadastro de condição de pagamento em src/condicao-pagamento.js: ele valida os dados (validarCondicao), grava, atualiza, exclui e lista pela API (cadastrarCondicao, atualizarCondicao, excluirCondicao, listarCondicoes) e monta a tela (criarTelaCondicao). A condição escolhida aparece depois no pedido, no campo "Cond.Pagt".

Desafio

Você, como aluno consultor, foi chamado para garantir a qualidade do cadastro de condição de pagamento. Escreva um único arquivo de teste, src/condicao-pagamento.test.js, para o único arquivo de código desta atividade, src/condicao-pagamento.js. Siga o padrão AAA (Arrange, Act, Assert), use o matcher mais específico em cada verificação, cubra os valores-limite e substitua a API por mocks onde for preciso provar como ela foi chamada.

O docente faz o teste junto com a turma, em sala, passo a passo (veja a aba "PRATICA AULA 03" no fim desta página): cada grupo de testes é escrito no quadro, digitado por todos, executado e lido em voz alta antes de seguir.

Regras do projeto: use apenas funções normais (function), sem arrow functions, e { } em todo if; não use async/await — encadeie as promessas com .then() e devolva-as com return. A API chega por parâmetro (injeção de dependência), por isso o teste pode trocá-la por uma API falsa ou por um mock.

Resultados esperados

  • Projeto do CRM rodando (npm run dev) com o menu "Cond. Pagto" funcionando.
  • O arquivo src/condicao-pagamento.test.js, com testes para as cinco funções: validarCondicao, cadastrarCondicao, atualizarCondicao, excluirCondicao e listarCondicoes.
  • No mínimo 8 testes, incluindo os valores-limite de parcelas (0, -1, 1.5 e texto).
  • Print do terminal com npx vitest run src/condicao-pagamento.test.js e todos os testes passando.

PRATICA AULA 03 — testando condicao-pagamento.js

Roteiro curto para o docente fazer com a turma, em sala, o arquivo src/condicao-pagamento.test.js. Os trechos vêm do arquivo src/condicao-pagamento.exemplo.test.js, que roda e está sempre passando.

1 Preparar: rodar, ler e criar o arquivo

No terminal, na pasta crm/, rode npm install e npm test (o Vitest roda de novo a cada vez que você salva). Leia o src/condicao-pagamento.js e crie o src/condicao-pagamento.test.js começando pelos import:

// 1.1 Ferramentas do Vitest: describe agrupa, it é um caso de teste, expect confere o resultado.
import { describe, it, expect, beforeEach, vi } from 'vitest';
// 1.2 A API falsa guarda os dados em memória: o teste não precisa do json-server ligado.
import { criarApiFalsa } from './api-falsa.js';
// 1.3 O que vamos testar (o arquivo de teste tem o nome do código + ".test.js").
import { cadastrarCondicao, listarCondicoes, validarCondicao } from './condicao-pagamento.js';

Não precisa ligar o json-server: o teste usa a API falsa em memória. Sem async/await.

2 validarCondicao: padrão AAA e valores-limite

// PASSO 2 — validarCondicao devolve uma LISTA de erros (lista vazia = tudo certo).
describe('validarCondicao', function () {
  it('devolve lista vazia para uma condição válida', function () {
    // Arrange (preparar): a condição que vamos avaliar
    const condicao = { nome: 'À vista', parcelas: 1 };

    // Act (agir): chamamos a função uma vez
    const erros = validarCondicao(condicao);

    // Assert (conferir): toEqual compara o CONTEÚDO da lista
    expect(erros).toEqual([]);
  });

  it('exige o nome', function () {
    expect(validarCondicao({ nome: '', parcelas: 1 })).toEqual(['Nome obrigatório']);
  });

  // it.each repete o teste para cada valor-limite (%s vira o valor)
  it.each([0, -1, 1.5, '2'])('recusa parcelas = %s', function (parcelas) {
    const erros = validarCondicao({ nome: 'À vista', parcelas });

    expect(erros).toContain('Parcelas deve ser um inteiro maior que zero');
  });
});

Arrange prepara, Act chama a função, Assert confere. toEqual compara o conteúdo da lista, toContain confere um item e it.each repete o teste para cada valor-limite.

3 cadastrarCondicao: promessas com a API falsa

// PASSO 3 — Promessas: o teste DEVOLVE (return) a promessa; sem o return ele passa sem conferir.
describe('cadastrarCondicao com API falsa', function () {
  let api;

  // beforeEach: um banco novo e vazio antes de CADA teste
  beforeEach(function () {
    api = criarApiFalsa();
  });

  it('cadastra e depois encontra a condição na lista', function () {
    const condicao = { nome: '30/60 dias', parcelas: 2 };

    return cadastrarCondicao(api, condicao)
      .then(function () {
        return listarCondicoes(api);
      })
      .then(function (lista) {
        expect(lista).toEqual([{ ...condicao, id: 1 }]);
      });
  });

  it('recusa dados inválidos com a mensagem do erro', function () {
    const invalida = cadastrarCondicao(api, { nome: '', parcelas: 1 });

    // rejects.toThrow: a promessa deve ser RECUSADA com esta mensagem
    return expect(invalida).rejects.toThrow('Nome obrigatório');
  });
});

Sem o return o teste termina antes do resultado chegar e passa sem conferir nada. O beforeEach cria um banco novo antes de cada teste e rejects.toThrow confere a recusa.

4 Mock: provar como a API foi chamada

// PASSO 4 — Mock: trocamos a API por um substituto para PROVAR como ela foi usada.
describe('cadastrarCondicao com mock da API', function () {
  it('chama api.criar na coleção "condicoes" com os dados', function () {
    const condicao = { nome: 'À vista', parcelas: 1 };
    // vi.fn() cria a função falsa; mockResolvedValue define o que ela devolve
    const api = { criar: vi.fn().mockResolvedValue({ id: 1, ...condicao }) };

    return cadastrarCondicao(api, condicao).then(function () {
      // toHaveBeenCalledWith confere os argumentos da chamada
      expect(api.criar).toHaveBeenCalledWith('condicoes', condicao);
    });
  });

  it('não chama api.criar quando os dados são inválidos', function () {
    const api = { criar: vi.fn() };

    return cadastrarCondicao(api, { nome: '', parcelas: 1 })
      .catch(function () {})
      .then(function () {
        // not.toHaveBeenCalled garante que NADA foi gravado
        expect(api.criar).not.toHaveBeenCalled();
      });
  });
});

vi.fn() cria a função falsa, toHaveBeenCalledWith confere os argumentos e not.toHaveBeenCalled prova que nada foi gravado.

5 Rodar, conferir e fechar

npx vitest run src/condicao-pagamento.test.js

  • ☐ Dinâmica "mutante sobrevivente": troque < 1 por <= 1 no código; algum teste deve falhar (se não falhar, escreva o que faltou) e depois desfaça.

PRATICA AULA 04 — Testes de integração com Testing Library

Aplicação da aula 04 no exemplo src/AULA-04.js (um formulário de cadastro) e no arquivo de testes src/AULA-04.test.js. Aqui o teste é de integração: ele monta o formulário num DOM simulado (JSDOM), digita e clica como o usuário e confere só o que aparece na tela (caixa preta, 3.1). Capacidades trabalhadas: C4 e C5; conhecimentos 2.3 (aplicação), 3.1 (teste funcional) e 4.1 (funcionalidade).

Estas aulas (04 a 06) usam async/await, porque toda ação do userEvent é assíncrona. A regra "sem async/await" vale só para a prática da aula 03.

1 O que o formulário faz (o código sob teste)

O formulário tem Nome, E-mail e Senha. O botão Cadastrar começa desabilitado e só habilita com nome preenchido, e-mail com @ e senha de pelo menos 6 caracteres. Com senha curta, aparece o aviso "A senha deve ter no mínimo 6 dígitos". Esta é a regra que os testes vão provar:

  function atualizar() {
    const senhaCurta = campoSenha.value.length > 0 && campoSenha.value.length < TAMANHO_MINIMO_SENHA;
    aviso.hidden = !senhaCurta;
    aviso.textContent = senhaCurta ? MSG_SENHA_CURTA : '';

    const senhaValida = campoSenha.value.length >= TAMANHO_MINIMO_SENHA;
    const estaCompleto = campoNome.value.trim() !== '' && campoEmail.value.includes('@');
    botao.disabled = !(estaCompleto && senhaValida);
  }

O teste não lê essas variáveis: ele só olha o resultado na tela. Por isso, se você trocar o nome de uma variável ou de uma classe CSS, os testes continuam passando.

2 Importar as ferramentas

import { describe, it, expect, vi, beforeEach } from 'vitest';
import '@testing-library/jest-dom/vitest';
import { screen } from '@testing-library/dom';
import userEvent from '@testing-library/user-event';
import { criarFormularioCadastro, MSG_SENHA_CURTA, MSG_SUCESSO } from './AULA-04.js';
  • describe, it, expect, vi e beforeEach: agrupar, descrever o caso, conferir, criar função falsa e preparar antes de cada teste.
  • @testing-library/jest-dom/vitest: ensina o expect os matchers do DOM (toBeDisabled, toBeVisible, toBeInTheDocument…). Como o vite.config.js deste projeto não tem setupFiles, o import fica no próprio arquivo.
  • screen: o "olho do usuário", que procura elementos na página.
  • userEvent: o "dedo do usuário", que digita e clica de verdade.

3 Arrange: montar o formulário antes de cada teste

describe('formulário de cadastro (aula 04)', () => {
  let aoCadastrar;
  let usuario;

  beforeEach(() => {
    document.body.innerHTML = '';
    aoCadastrar = vi.fn();
    usuario = userEvent.setup();
    document.body.append(criarFormularioCadastro({ aoCadastrar }));
  });
  • document.body.innerHTML = '' limpa a página: um teste nunca enxerga o resto do outro.
  • vi.fn() cria o aoCadastrar falso, só para saber se (e com quais dados) o formulário o chamou.
  • userEvent.setup() cria o "usuário" que dispara foco, teclado e clique na ordem real.
  • document.body.append(...) coloca o formulário na página, como o navegador faria.

4 Act e Assert: caso do plano → teste (senha de 5 caracteres)

  it('mostra o aviso e mantém o botão desabilitado com senha de 5 caracteres', async () => {
    await usuario.type(screen.getByLabelText('Nome'), 'Ana');
    await usuario.type(screen.getByLabelText('E-mail'), 'ana@email.com');
    await usuario.type(screen.getByLabelText('Senha'), '12345');

    expect(screen.getByRole('button', { name: 'Cadastrar' })).toBeDisabled();

5 Corrigir a senha: o aviso some e o botão habilita

  it('habilita o botão e some com o aviso ao corrigir a senha', async () => {
    await usuario.type(screen.getByLabelText('Nome'), 'Ana');
    await usuario.type(screen.getByLabelText('E-mail'), 'ana@email.com');

queryByText devolve null quando não acha, por isso serve para provar que algo não está na tela (not.toBeInTheDocument()). Já getByText falharia o teste ao não achar. O mesmo campo recebe "123" e depois "456" (total 123456), simulando o usuário que percebe o aviso e continua digitando.

Aqui o teste percorre o caminho completo do usuário. toHaveBeenCalledWith prova que o formulário entregou ao callback exatamente os dados digitados, e getByRole('status') confere a mensagem de sucesso. Um único teste cobre digitação, validação, envio e resposta: por isso é de integração, e não unitário.

PRATICA AULA 05 — Integração avançada e mock de APIs

Aplicação da aula 05 no exemplo src/AULA-05.js (tela de login e carrinho) e nos testes src/AULA-05.test.js. O objetivo é o teste não depender da API real: a resposta do servidor é simulada e o teste controla exatamente o que ela devolve, inclusive os erros 500 e 404 e a rede lenta (confiabilidade, 4.3). Capacidade trabalhada: C5; conhecimentos 2.3, 4.3 e 7.3.

A aula apresenta o MSW, mas ele não está instalado neste projeto. Usamos a opção listada na própria aula para casos simples: vi.spyOn(globalThis, 'fetch'), que troca o fetch global por uma função controlada pelo teste. O código da tela não muda nada.

1 O código sob teste: cada resposta vira uma mensagem

async function interpretarResposta(resposta) {
  if (resposta.status >= STATUS_ERRO_SERVIDOR) return MSG_SERVICO_INDISPONIVEL;
  if (resposta.status === STATUS_NAO_ENCONTRADO) return MSG_NAO_ENCONTRADO;

  const dados = await resposta.json();
  if (resposta.status === STATUS_NAO_AUTORIZADO) return dados.erro;
  if (!resposta.ok) return MSG_SERVICO_INDISPONIVEL;

  localStorage.setItem(CHAVE_TOKEN, dados.token);
  return `Bem-vindo, ${dados.nome}`;
}

Repare em duas decisões de confiabilidade: o erro 500 devolve a mensagem sem chamar resposta.json() (servidor fora do ar costuma responder sem corpo, e o json() lançaria um erro), e a tela usa try/catch/finally para tratar a rede caída e sempre reativar o botão. Os testes abaixo existem para provar essas duas decisões.

2 Resposta falsa e atalho do login

/**
 * Cria uma resposta no formato mínimo de Response usado pela tela.
 * @param {number} status - Código HTTP.
 * @param {object} [corpo] - Corpo JSON; sem corpo, json() rejeita.
 * @returns {{ok: boolean, status: number, json: Function}} Resposta simulada.
 */
function responder(status, corpo) {
  return {
    ok: status >= 200 && status < 300,
    status,
    json: () => (corpo === undefined ? Promise.reject(new Error('vazio')) : Promise.resolve(corpo)),
  };
}

/**
 * Preenche o formulário de login e clica em Entrar.
 * @param {string} email - E-mail digitado.
 * @param {string} senha - Senha digitada.
 * @returns {Promise<void>} Conclui após o clique.
 */
async function entrarCom(email, senha) {
  const usuario = userEvent.setup();
  await usuario.type(screen.getByLabelText('E-mail'), email);
  await usuario.type(screen.getByLabelText('Senha'), senha);
  await usuario.click(screen.getByRole('button', { name: 'Entrar' }));
}
  • responder(status, corpo) monta só o pedaço da Response que a tela usa (ok, status e json). Sem corpo, o json() rejeita, como num erro 500 real sem corpo.
  • entrarCom(email, senha) evita repetir o Act em todo teste: digita, digita e clica.

3 Isolamento: nada vaza de um teste para o outro

describe('fluxo de login', () => {
  beforeEach(() => {
    document.body.innerHTML = '';
    localStorage.clear();
    montarTelaLogin(document.body);
  });

  afterEach(() => {
    localStorage.clear();
    vi.restoreAllMocks();
  });

Antes de cada teste a página e o localStorage são limpos e a tela é montada de novo. Depois, vi.restoreAllMocks() devolve o fetch verdadeiro (é o papel que o resetHandlers() teria com o MSW). Sem isso, a resposta falsa de um teste vazaria para o seguinte e o resultado dependeria da ordem de execução.

4 Sucesso: provar a resposta e também a requisição

  it('sucesso: envia as credenciais, guarda o token e dá boas-vindas', async () => {
    const espiao = vi
      .spyOn(globalThis, 'fetch')
      .mockResolvedValue(responder(200, { token: 'abc123', nome: 'Aluno' }));

    await entrarCom('aluno@email.com', 'senha123');

    expect(await screen.findByText('Bem-vindo, Aluno')).toBeVisible();
    expect(localStorage.getItem(CHAVE_TOKEN)).toBe('abc123');
    const [url, opcoes] = espiao.mock.calls[0];
    expect(url).toBe(`${URL_API}/login`);
    expect(opcoes.method).toBe('POST');
    expect(JSON.parse(opcoes.body)).toEqual({ email: 'aluno@email.com', senha: 'senha123' });
  });
  • mockResolvedValue define o que o fetch falso devolve.
  • findByText espera a mensagem aparecer (o login é assíncrono). Nunca use setTimeout fixo: deixa o teste lento quando sobra e instável (flaky) quando falta.
  • espiao.mock.calls[0] guarda como o fetch foi chamado: prova a URL, o método POST e o corpo JSON enviado. O mock também serve para auditar a requisição.

6 Rede lenta e rede caída

  it('rede lenta: mostra Carregando e depois o resultado', async () => {
    let liberarResposta;
    vi.spyOn(globalThis, 'fetch').mockReturnValue(
      new Promise((resolver) => {
        liberarResposta = resolver;
      }),
    );

    await entrarCom('aluno@email.com', 'senha123');
    expect(await screen.findByText(MSG_CARREGANDO)).toBeVisible();
    liberarResposta(responder(200, { token: 'abc123', nome: 'Aluno' }));

    expect(await screen.findByText('Bem-vindo, Aluno')).toBeVisible();
    await waitFor(() => expect(screen.queryByText(MSG_CARREGANDO)).not.toBeInTheDocument());
  });

  it('rede caída: mostra sem conexão', async () => {
    vi.spyOn(globalThis, 'fetch').mockRejectedValue(new TypeError('Failed to fetch'));

    await entrarCom('aluno@email.com', 'senha123');

    expect(await screen.findByText(MSG_SEM_CONEXAO)).toBeVisible();
    expect(localStorage.getItem(CHAVE_TOKEN)).toBeNull();
  });

Na rede lenta, a promessa do fetch fica pendente até o próprio teste chamar liberarResposta(...). Assim dá para conferir o "Carregando..." no meio do caminho e depois o resultado, sem relógio nenhum. waitFor fecha provando que o aviso de carregamento foi retirado. Na rede caída, mockRejectedValue(new TypeError(...)) faz o fetch rejeitar, como acontece sem internet, e a tela deve cair no catch.

PRATICA AULA 06 — Testes end-to-end (fluxo completo)

Aplicação da aula 06 no exemplo src/AULA-06.js (uma mini-loja com login, painel, carrinho, checkout e confirmação) e nos testes src/AULA-06.test.js. O E2E percorre o caminho completo do usuário e confere o resultado de cada etapa. Capacidades: C4 e C5; conhecimentos 2.2, 2.3, 3.1 e 4.2 (usabilidade).

Cypress e Playwright não estão instalados e este projeto não abre navegador para validar. Por isso o fluxo é simulado em JSDOM com Vitest e Testing Library. A lógica é a da aula: passos de usuário e uma verificação depois de cada etapa. Trocar por Playwright muda só a ferramenta (veja o passo 6).

1 O que a loja faz (o código sob teste)

PáginaO que o usuário vê e faz
loginE-mail, senha e botão Entrar; credencial errada mostra um alerta
painel"Bem-vindo, Aluno", produto Caderno (R$ 20), Adicionar ao carrinho e contador de itens
carrinhoQuantidade e "Subtotal: R$ ..." recalculado a cada alteração
checkoutEndereço e cartão de teste (16 dígitos); Confirmar só habilita com os dois válidos

A função montarLoja(container) controla a troca de página sozinha e marca a página atual no atributo data-pagina, mas o teste não usa esse atributo: ele só olha títulos, rótulos e botões, como um usuário (caixa preta, 3.1).

2 Arrange: dados isolados e o atalho de login

4 Fluxo de checkout: cada etapa tem uma verificação

  it('checkout completo: login, carrinho, checkout e confirmação', async () => {
    await entrar();

    await usuario.click(screen.getByRole('button', { name: 'Adicionar ao carrinho' }));

5 Usabilidade (4.2): rótulos, papéis e teclado

  it('usabilidade 4.2: campos por label e botões por papel', () => {
    expect(screen.getByLabelText('E-mail')).toBeInTheDocument();
    expect(screen.getByLabelText('Senha')).toBeInTheDocument();
    expect(screen.getByRole('button', { name: 'Entrar' })).toBeInTheDocument();
  });

  it('fluxo de login só com teclado', async () => {
    await usuario.tab();
    expect(screen.getByLabelText('E-mail')).toHaveFocus();
    await usuario.keyboard(EMAIL_VALIDO);

    await usuario.tab();
    expect(screen.getByLabelText('Senha')).toHaveFocus();
    await usuario.keyboard(SENHA_VALIDA);
    await usuario.keyboard('{Enter}');

    expect(screen.getByRole('heading', { name: 'Painel' })).toBeInTheDocument();
  });

O primeiro teste garante que os campos têm rótulo e os botões têm nome (acessibilidade). O segundo faz o login só com o teclado: tab() move o foco, toHaveFocus() prova onde ele está e {Enter} envia o formulário. Se o campo não fosse alcançável por teclado, o teste falharia.
